## Publish attempt — BLOCKED by a new database constraint, not an editorial failure

Drafted the OSU/Moritz story fully to spec (`frontend/prompts/ARTICLE_WRITING.md`, `article-submission.schema.json`, the copywriting skill): 6 H2s, 747-word body, 6-source ledger (1 primary — the OSU Board of Trustees' June 2026 meeting record — 5 secondary), 16-entry claim ledger with every numeric/dated/status sentence mapped, 8-entry entity ledger, full image brief with truthful AI-disclosure provenance.

`node scripts/publish-article.mjs` ran the full deterministic editorial gate (A0–A15) and **the article passed every check** — answer-first, local scope, tags, source floor, claim traceability, number traceability, entity verification, quote integrity, status labels, no hype/promotional language, 350+ words, SEO metadata, web structure, originality/disclosure all PASS.

It then failed at the database INSERT with a **new PostgreSQL check constraint, `articles_live_image_required`**, that did not exist as of the Sep 13 Session 2 run (which published `image_url: null` articles successfully — see `frontend/content/articles/2026-09-12-*.json` and `2026-09-13-*.json`, both still `image_url: null` in the repo and still live). The constraint requires `status <> 'live' OR (image_url IS NOT NULL AND image_url LIKE 'https://%')`. I confirmed by direct query (`pg_get_constraintdef`) that this exists in the live database; it is **not defined anywhere in the repository** — no migration script under `scripts/migrate-*` references it, and no commit since Sep 13 touches any `scripts/*image*` file. It was added directly against production, bypassing the repo.

This directly contradicts CLAUDE.md ("Images never block publication") and the copywriting skill, and it breaks `publish-article.mjs`'s own designed flow: the script intentionally inserts with `image_url = null` and attaches a placeholder card (`hostPlaceholderCard`) *after* the row exists — but the new constraint now rejects the insert itself, before the placeholder step ever runs. I confirmed there is no workaround available in this session:
- `BLOB_READ_WRITE_TOKEN` is not set, so `hostPlaceholderCard`'s only https:// path (Vercel Blob) is unavailable; its fallback (`/images/heroes/<id>.webp`, a local path) cannot satisfy the constraint's `https://` requirement anyway, and CLAUDE.md itself says local `/images/heroes/` paths "are not publication images."
- The Higgsfield CLI install timed out again (`npm install -g @higgsfield/cli`, same failure mode as Sep 13), so no real hero image could be generated either.
- The only pre-approved durable hosts are `images.unsplash.com`, `*.cloudfront.net`, and `*.public.blob.vercel-storage.com` (`scripts/article-image-policy.mjs`) — I did not have a genuine, specific, truthfully-captioned photo of this exact building available to use honestly, and fabricating or mismatching an image would violate the truthful-provenance requirement.

Per CLAUDE.md ("Never bypass the script or write a row directly"), I did not hand-write an INSERT to get around this. **The fully gate-passed draft is committed at `frontend/content/articles/2026-09-14-osu-moves-moritz-college-of-law-downtown-into-huntington-tower.json`** — ready to publish via the normal script the moment an image credential is available (Higgsfield or `BLOB_READ_WRITE_TOKEN`), with no further editorial rework needed.

**This is a new, severe finding: the newsroom's core publish path is currently blocked for every session that lacks image-hosting credentials — which has been most sessions for weeks.** It is a plausible explanation for why AM-session publishing has produced zero live articles even on the rare day `DATABASE_URL` was present. Recommend the owner either (a) add `BLOB_READ_WRITE_TOKEN` to the routine environment, (b) fix the Higgsfield credential/CLI issue, or (c) relax the constraint to match the documented policy and let `hostPlaceholderCard`'s existing post-insert flow do its job. Flagging by push notification given the severity.
