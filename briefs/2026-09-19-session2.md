## What is still broken — the actual publish blocker

Despite DB access working, **every publish attempt still fails**, confirmed live:

```
NeonDbError: new row for relation "articles" violates check constraint "articles_live_image_required"
```

Root cause, verified by reading `scripts/publish-article.mjs` and `scripts/article-image-policy.mjs`:
- The `articles` table has a DB-level check constraint requiring `image_url IS NOT NULL` for any row with `status='live'`.
- `publish-article.mjs` inserts the row with `image_url = null` first, then *tries* to attach a branded placeholder card afterward — but the INSERT itself is rejected by the constraint before that placeholder step ever runs.
- The placeholder-hosting step (`hostPlaceholderCard`) requires `BLOB_READ_WRITE_TOKEN`, which is **not set** in this environment.
- The only URLs the policy accepts as "durable" are `images.unsplash.com`, `*.cloudfront.net`, or `*.public.blob.vercel-storage.com` (`isDurableArticleImageUrl`). Without blob-hosting access, there is no policy-compliant image_url to supply — and substituting a generic stock photo for a specific building/story would violate CREN's truthful-provenance rule (this exact reasoning is also recorded in `briefs/2026-09-14-run2.md` and `briefs/2026-09-11.md`).

**This has been the true blocker since at least Sept. 11**, but was masked on most days by `DATABASE_URL` also being absent. Today is the first day both pieces could be tested together, and it confirms: **restoring `DATABASE_URL` alone will not unblock publishing.** `BLOB_READ_WRITE_TOKEN` must also be set in the routine's environment config for a single article to go live.

I did not attempt any workaround (no `--allow-deploy-lag`, no non-durable image_url, no bypassing the script) — the repo gate is intentional and CLAUDE.md is explicit that this script must not be bypassed.
