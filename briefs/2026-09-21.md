The snapshot fallback used on DB-less days was simply one week stale, which made the backlog look larger than it is. 104 live articles total per `verify:site`.

**What actually blocks 09-13 through today:** the `articles` table carries
```
CHECK (status <> 'live' OR (NULLIF(btrim(image_url), '') IS NOT NULL AND image_url LIKE 'https://%'))
```
`publish-article.mjs` inserts the row first and only attaches a placeholder hero *after* the insert succeeds — so with no durable `https://` image ready at insert time, the `INSERT` itself fails the constraint before the placeholder logic ever runs. Confirmed live: attempting to publish the stranded 09-14 OSU Moritz article (content-gate clean, per Sep 20 notes) failed with `NeonDbError: ... violates check constraint "articles_live_image_required"`.

Both paths to a durable image are unavailable this session:
- `BLOB_READ_WRITE_TOKEN` is not set → `hostPlaceholderCard()` can't upload to Vercel Blob and falls back to writing a local `/images/heroes/...` file, which the DB constraint rejects anyway (not `https://`) and which wouldn't resolve until a deploy regardless.
- Higgsfield (image generation) is configured but network calls return "no response received" → `IMAGES_OFF`, same cloud-egress restriction previously reported for `columbusrealestatenews.com`.

**Net effect: no article — old or new, any content quality — can go live from this cloud routine until one of those two paths works.** This is a harder blocker than "DATABASE_URL absent," and it is why every DB-restored session so far has still failed to publish. Per CLAUDE.md, this session did not bypass the gate, edit the constraint, or write a row directly.
