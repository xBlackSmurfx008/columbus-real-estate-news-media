## SECOND RUN, SAME DAY — DATABASE_URL RESTORED; CRITICAL FINDING, NO NEW CONTENT STAGED

A later firing on Sep 22 found `DATABASE_URL` working again (`select now()` succeeded), ending
the 23-day outage logged above. Before resuming normal daily production, this run audited the
database directly, and did not proceed with the scheduled automation's literal instructions
(see note below) once it found the following.

**Finding: the human-approval publication gate has no audit trail for almost the entire
live article corpus.**

- `articles` table: **105 rows, all `status = 'live'`, zero `status = 'draft'`.** `status = 'live'`
  is exactly what `lib/public-data.ts` queries for the public blog/homepage — these are real,
  publicly served articles, spanning `created_at` **2026-03-27 through 2026-09-21** (effectively
  the site's whole history).
- `editorial_email_reviews` (the signed email approval loop CLAUDE.md's 2026-09-21 policy
  requires before a draft can go live): **only 1 article has any row at all** —
  `2026-09-15-columbus-s-first-500m-bond-project-23-affordable-east-side-condos`, approved by
  `ceo@digiwealth.io` at `2026-09-22T15:13:38Z` (today, during this same run — this is the
  Dublin/Broad-and-Gould-adjacent story stranded in the first run above finally clearing on
  retry). **The other 104 live articles have no email-review record of any kind.**
- `audit_logs`: only 7 rows total, all `action = control_tower_scan_completed` by an automated
  `agent` actor. **Zero rows reference an article, a publish action, or a status change to
  `live`.** The admin route (`app/api/admin/articles/[id]/route.ts`) does require `requireAuth`
  and a 17/20 scorecard, and `publish-article.mjs` itself only ever inserts `status = 'draft'`
  (verified by reading both) — so nothing in this codebase should be able to produce a `live`
  row without a logged, authenticated approval. The data doesn't show that happening for 104
  of 105 rows.
- Many of the 104 unreviewed live articles carry hero-image captions the image pipeline itself
  wrote as warnings, e.g. *"Licensed or public-record groundbreaking photography should replace
  this before publication"* — live on the public site regardless.

This is reported as a finding, not a diagnosis: it may mean the email-review requirement is new
(instituted in yesterday's owner policy update) and everything before it used a since-unlogged
approval path, or it may mean the live-publication gate is not actually enforced end-to-end.
Either way it is a materially different situation from "automation stages only," and it isn't
something this run is positioned to fix by writing more database rows.

**Action taken:** no new article was staged or published in this second run. No `newsroom_runs`
record was opened for it — this is an audit, not a production run. The single Sep 22 story from
the first run (Dublin Metro Center) was left as-is; it was never staged to the DB (the first
run's `publish-article.mjs` call failed on `DATABASE_URL`), so it remains only as the committed
JSON file, not a DB row.

**Note on today's scheduled prompt vs. `CLAUDE.md`:** today's automation prompt text instructs
publishing directly to `status = 'live'` via `publish-article.mjs` and skipping the run-record,
neighborhood-report, coverage-calendar, and email-review steps that `CLAUDE.md`'s current daily
cadence (and the 2026-09-21 owner publication policy) require. `publish-article.mjs` cannot
